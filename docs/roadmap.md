# MyKeep Delivery Roadmap

MyKeep is delivered in eight dependency-ordered phases. A phase begins only after its prerequisites have been approved and merged. The detailed work items and dependency edges are maintained in the [issue map](issue-map.md).

| Phase | Outcome | Prerequisites | Completion gate |
| --- | --- | --- | --- |
| 1. Foundation | The approved architecture, governance policies, contribution workflow, security policy, templates, delivery roadmap, and GitHub planning model are established. | Approved foundation design. | Issue #1 is reviewed, all documentation checks pass, and its PR is approved and merged without application features. |
| 2. Tooling | A React/TypeScript/Vite/Tailwind/Vitest frontend and Python 3.12+/FastAPI/pytest backend have a minimal monorepo structure and repeatable local and CI quality gates. | Foundation. | Clean checkouts can install dependencies and CI passes formatting, linting, type checks, tests, frontend production build, dependency/security checks, and secret scanning. |
| 3. Persistence | Supabase PostgreSQL, the private `mykeep` bucket, row-level security, migrations, and operator-only member provisioning enforce the approved data and ownership model. | Tooling. | Migrations apply and roll back in a non-production project; RLS and Storage tests prove isolation; an operator can provision, disable, and remove a member without exposing raw LINE identities. |
| 4. Authentication | FastAPI verifies raw LINE ID tokens server-side and issues short-lived, revocable MyKeep sessions only to approved, enabled members. | Persistence. | Automated tests cover issuer, audience, expiry, subject hashing, disabled and unknown members, cookie controls, rotation, revocation, and per-request member-status checks. |
| 5. File API | Authenticated members can upload, list, search, download, rename, soft-delete, restore, and eventually purge only their own files through FastAPI. | Authentication and private persistence. | API, database, and Storage tests cover the complete lifecycle, safe cleanup, opaque paths, signed downloads, common `404` behavior, and owner-success/cross-member-denial cases for every file endpoint. |
| 6. LIFF UI | The LIFF client provides the approved-member sign-in handoff and a responsive file-management experience without making authorization decisions or receiving server secrets. | Authentication and file API. | Production builds and UI tests pass; end-to-end tests cover LIFF handoff and the supported file workflows, progress and error states, and access denial. |
| 7. Reliability and security | Recovery jobs, auditing, observability, operational limits, redaction, and security hardening make the complete application supportable. | File API and LIFF UI. | Purge and audit jobs, rate and size limits, security headers, redaction, health/readiness behavior, backup procedures, and dependency/security checks pass documented tests and review. |
| 8. Staging acceptance | The frontend, backend, and isolated staging Supabase project are deployed and validated as an integrated system. | Reliability and security. | Container and Vercel deployments are reproducible; exact-origin CORS and secret configuration are verified; staging acceptance, cross-member isolation, and a documented restore exercise pass before production approval. |

Production deployment is outside these phase gates and always requires explicit approval.
